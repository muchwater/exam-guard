# 실측 캡처 v1: spark3(MT7925)를 sniffer로 (2026-11-26)

## 결론
- 연구실 머신 spark3의 내장 Wi-Fi(MediaTek MT7925, 드라이버 `mt7925e`)는 monitor mode에서 **다른 기기 사이의 HT 데이터 프레임을 잡는다**. RTL8192EU와 대조된다(`docs/monitor_mode_test.md`).
- 이제 실제 업로드 패킷을 기록할 수 있다. 라이브로 캡처할 필요가 없는 오프라인 replay 데모에는 이 방식으로 충분하다.
- 합성 데이터로 보정한 detector를 **그대로** 실측에 적용한 결과:
  - window model: 업로드 10/10을 잡았지만 오탐이 4건 있었다.
  - rule: 오탐은 0건이지만 업로드를 5/10만 잡았다(VGA 0/5).
  - 둘 다 실측 데이터로 다시 보정해야 한다.

## 구성
| 항목 | 값 |
|---|---|
| 업로드 기기 | Rubik Pi 3 wlan0 (Broadcom AP6256), AP `inalab` 채널 2, HT20 |
| 업로드 경로 | wlan0 → AP → 유선 → 보드 유선 포트의 macvlan(netns `egsrv`). IPv6 link-local `%wlan0`이라 반드시 무선을 지난다 |
| sniffer | spark3 `wlP9s9`(MT7925, kernel 6.17.0-1014-nvidia). 평소 미사용 Wi-Fi라 monitor 전환이 spark3 연결에 영향 없음 |
| 캡처 스크립트 | `tools/linux_monitor_capture.sh` (sudo 1회, BPF로 보드 MAC만, 정지 파일 또는 시간 초과 시 managed로 복원) |
| 트래픽 | 시계 표식 → ping 20회(1400 B) → VGA 업로드 5회 → UXGA 업로드 5회 → 2 MB 다운로드 5회 → 시계 표식 |
| 원본 | `data/raw/real/spark3_20261126/` (git 제외, pcap sha256은 `data/measured/real_capture_spark3_v1.json`) |

- **개인정보:** 디스크에 남은 프레임 20,206개 중 보드 MAC과 무관한 것은 0개였다.
- **잡힌 프레임 구성:** QoS 데이터 16,698(보드 송신 6,779, 보드 수신 9,978), BlockAck 1,978, RTS 693, CTS 680.

## 시계 맞추기 (in-band 표식)
- 보드가 크기가 서로 다른 IPv6 UDP 10개(payload 1000+7i B)를 보내며, 보낸 시각을 보드 시계로 기록했다.
- 캡처에서 같은 크기의 프레임(MPDU = payload + 98 B)을 찾았다.
  - 98 B = QoS 헤더 26 + CCMP 8 + LLC 8 + IPv6 40 + UDP 8 + MIC 8
- 결과: 보드 시계 − spark3 시계 = **−0.591 s** (표식 19개의 중앙값).
  - 시작과 끝(약 2분 30초 간격)의 값 차이가 1 ms 수준이었다.
  - 오차는 송신 큐와 전송 지연(ms 이하)만큼이다.
- spark3는 NTP 동기화가 안 되어 있었으므로(`timedatectl`: NTPSynchronized=no), 매 캡처마다 표식이 필요하다.

## 물리 측정 (업로드 구간 ±50 ms)
| | 업로드 VGA 114,993 B × 5 | 업로드 UXGA 528,833 B × 5 | 다운로드 2 MB × 5 |
|---|---|---|---|
| 보드 송신 데이터 프레임 | 87–91 | 320–425 | 673–1,105 (122 B TCP ACK) |
| 공기 중 업링크 바이트 | 124,459–128,480 | 482,694–646,485 | 82,407–135,015 |
| 큰 프레임(≥1530 B) 비율 | 0.879–0.920 | 0.965–0.983 | 0 |
| 최대 IAT | 6.2–9.9 ms | 8.2–109.8 ms | 29–48 ms |
| 업링크 지속 | 44–51 ms | 143–308 ms | 478–660 ms |

- 업링크 데이터 프레임의 14%가 재전송(retry)이었다.
- UXGA에서 공기 중 바이트가 payload보다 적은 경우(482,694 B)가 있다. 그 구간에 sniffer가 놓친 프레임이 있다는 뜻이다(TBD: 손실률 측정).

## Detector 결과 (설정: `configs/netsim_v1_derived.yaml`, 합성 보정 그대로)
| detector | 업로드 탐지 | 오탐 | 다운로드 중 오탐 |
|---|---|---|---|
| rule | 5/10 (UXGA 5/5, VGA 0/5) | 0 | 0 |
| window model | **10/10** | 4 | 0 |

- **rule이 VGA를 놓친 이유:** 합성 보정값이 실측보다 빡빡했다.
  - 실측 VGA의 업링크 바이트(124–128 KB)가 `min_burst_bytes` 130,653 B보다 작았다.
  - 큰 프레임 비율(0.879–0.920)도 `min_large_ratio` 0.924보다 낮았다.
  - 원인 후보는 셋이다: 재전송, IPv6(같은 1550 B 프레임에 payload가 20 B 적음), 합성과 다른 리사이즈(center crop 유무).
- **window model 오탐 4건:** 모두 데이터 양은 아주 적지만 큰 프레임만 드문드문 나가는 구간이었다.
  - ping 1400 B를 0.5 s 간격으로 보낸 구간: 점수 0.92, 0.90
  - 시계 표식(1 KB UDP 5개/s) 구간: 점수 0.32, 0.34. threshold 0.3065 바로 위다.
  - 합성 학습 데이터에는 이런 배경 트래픽이 없었다.
- **onset 오차:** window model은 −0.81 s(중앙값)였다. event 시작을 1 s 창의 시작으로 잡기 때문이다.

## 다음 단계
1. **실측 보정 세션을 녹화한다.** 해상도와 간격을 바꾼 업로드 수십 회에, 배경 트래픽(유휴, 웹 브라우징형 다운로드, 주기적 소량 업링크)을 섞는다. 이 데이터로 rule 값과 window model을 다시 보정한다. LOSO 방식이고, `net_event.calibrate`의 규칙은 그대로 쓴다.
2. **데모용 세션을 녹화한다.** 팀원이 연기한 영상과 spark3 캡처를 함께 녹화하고, 표식으로 시계를 맞춘다.
3. **Sniffer 손실률을 측정한다.** 서버가 받은 바이트와 캡처된 업링크 바이트를 비교한다.
